## Overview

ClipGuardian started with a question I had while learning about data security and information disclosure: **we copy sensitive information all the time, so what happens to it after we press `Ctrl + C`?**

Passwords, email addresses, payment details, API keys, crypto wallet addresses, personal identifiers — a lot of things we would never want to expose casually pass through the clipboard. We copy something, paste it somewhere, and move on. The clipboard is useful, but it is also another place where sensitive data can sit around or be accessed by other software running on the same machine.

That made me wonder why we don't pay more attention to clipboard security. What if someone accidentally leaves a password or token copied? What if malware or another unwanted process reads or changes the clipboard? A small mistake could become an information-disclosure problem, and clipboard hijacking can make the risk more than just theoretical.

So I built **ClipGuardian**, a Windows-focused clipboard monitoring tool that watches for new copied text, checks it for selected sensitive-data patterns and risky content, and warns the user when something deserves attention. I also wanted quick ways to inspect or clear the clipboard, plus reminders so that sensitive content does not stay there longer than necessary.

This is a completed academic prototype exploring one often-overlooked part of everyday data handling. It is not a production-ready security product, a full Data Loss Prevention (DLP) platform, or a replacement for endpoint protection.

## What I built

The current project is a Python application for Windows with a Tkinter interface and a background clipboard-monitoring loop. When monitoring is enabled, the tool checks for clipboard changes and examines new text against a collection of patterns and heuristics.

The project report and public code describe these main features:

- **Sensitive-data pattern checks** for items such as email addresses, payment card numbers, phone numbers, US-style SSNs, IP addresses, API-key-like strings, AWS credential patterns, private-key markers, and Bitcoin, Ethereum, and Solana wallet addresses.
- **Password-related checks**, using simple heuristics to decide whether copied text looks like a password and a Have I Been Pwned (HIBP) lookup to check for known exposure.
- **Risky-command detection** for a small set of recognizable destructive shell or Windows commands. When one of these patterns is detected, the current code attempts to clear the clipboard rather than leave the command ready to paste.
- **URL checks** through a Google Safe Browsing API integration path, with a configurable domain whitelist.
- **Windows toast notifications** when selected sensitive or risky content is detected.
- **Clear-clipboard reminders** with a configurable delay, so the user gets a nudge to remove sensitive content after copying it.
- **Global hotkeys** for clearing the clipboard, inspecting its current contents, and toggling monitoring.
- **A small GUI** with Main, Settings, and About tabs, light/dark themes, a recent clipboard-history view, and options for enabling or disabling checks.
- **Windows startup integration**, which can add or remove an entry under the current user's Run registry key.

The idea was to make the user aware of what they had copied and give them a fast next action. A notification alone cannot stop every clipboard attack, but it can make an otherwise invisible event visible.

## How it works

The core workflow is straightforward:

1. **Watch for clipboard changes.** A background thread polls the Windows clipboard roughly every half-second while monitoring is active. It compares new text with recent content to avoid repeatedly processing the same copy.
2. **Keep a short in-memory history.** New clipboard text is added to the application's history list for display in the GUI. The default history limit in the code is 50 entries.
3. **Check for sensitive patterns.** Regular expressions look for known formats such as card numbers, emails, phone numbers, wallet addresses, API-key patterns, and private-key markers. These checks are pattern-based, so they are clues rather than perfect identification.
4. **Check other risky content.** The tool looks for a small set of hard-coded destructive command patterns, scans text for URLs, and applies a heuristic to decide whether content might be a password.
5. **Use external checks when enabled and configured.** URL reputation checking uses Google Safe Browsing. The password-breach check uses the HIBP Pwned Passwords range endpoint.
6. **Notify and remind.** When a configured detection fires, ClipGuardian can show a Windows notification and, for recognised sensitive data, schedule a reminder to clear the clipboard.
7. **Let the user act.** The GUI and global hotkeys provide quick access to inspection, monitoring controls, and clipboard clearing.

The implementation uses a polling loop rather than an operating-system event subscription. It is a relatively simple approach for a personal Windows utility, but it also means clipboard checks are periodic and limited to text content the code can read.

## The checks are patterns, not magic

A useful part of this project was thinking about what it actually means to detect sensitive data. Some values have recognizable formats: an Ethereum address, an email address, or an AWS access-key ID can be matched by a pattern. Other data is harder to classify. A random string might be a password, an API token, or simply text that happens to look complex.

ClipGuardian therefore combines regular expressions with basic heuristics. The password logic considers features such as length, character variety, URLs, and recent clipboard entries. That is a practical starting point, but it will inevitably miss some real secrets and flag some harmless text. It is not a trained classifier, and the project report does not establish measured precision or recall for these detections.

The URL and password-breach checks add another type of signal, but they also depend on external services and network availability. They should be treated as assistance for the user, not as a guarantee that a URL is safe or a password is uncompromised.

## Quick actions and the interface

The GUI was designed around a few actions that I wanted to be easy to reach without digging through menus:

| Shortcut | Action |
| --- | --- |
| `Ctrl + Shift + C` | Clear the clipboard and the tool's visible history |
| `Ctrl + Shift + I` | Open a clipboard-inspection window |
| `Ctrl + Shift + M` | Toggle clipboard monitoring on or off |

The Settings tab includes controls for selected detection features, reminders, API configuration, URL-whitelist domains, and Windows auto-start. The Main tab displays monitoring status and recent clipboard history. The interface also includes light and dark themes.

The recent-history view is held in memory by the running application rather than designed as a persistent clipboard archive. The code limits the history and provides a clear-history action. However, the logging caveat below means I would not claim that clipboard text can never reach a disk log in this version.

## Privacy was part of the idea — and there is a trade-off

I wanted the tool to run on the user's own Windows device rather than upload a full clipboard history to a central service. Pattern matching and the normal monitoring loop happen locally, and the app keeps its recent clipboard history in memory while it is running.

But I also wanted more useful checks than local patterns alone could provide. That introduces a trade-off:

- **Google Safe Browsing:** when the URL check is used, the candidate URL is sent to Google's Safe Browsing API for reputation checking. That is not a fully local check.
- **Have I Been Pwned:** the code hashes a candidate password with SHA-1 and sends the first five hexadecimal characters to the Pwned Passwords range endpoint. It compares the returned suffixes locally rather than sending the original password as plain text. This reduces what is disclosed to the service, but it is still an external request.
- **Configuration:** API settings are saved in a local `config.json` file by the current code. Real API keys in that file should be treated as secrets and should never be committed to a public repository.

So my original intention was local-first clipboard monitoring, not a claim that every feature works fully offline. If I were extending the project, I would make the privacy choices more explicit in the interface and explain clearly when a copied URL or password-derived value is sent to an external service.

## A connection to OWASP and DLP

I connected this idea to **OWASP Top 10 A04:2021 — Insecure Design** because it made me think about a design blind spot: an ordinary, convenient workflow can expose sensitive data if the system does not help people manage the risk. Clipboard use is not itself an OWASP vulnerability, and ClipGuardian does not make an application formally compliant with the OWASP Top 10. I see the connection as a design lesson: account for how sensitive information is handled in normal user workflows, not only in obvious attack paths.

The idea also overlaps conceptually with **Data Loss Prevention (DLP)**: both are concerned with sensitive information moving through systems. ClipGuardian is much narrower. It is a small, single-user Windows prototype, not an enterprise DLP solution with organization-wide policies, endpoint fleet management, centralized auditing, or guaranteed prevention controls.

## Limitations and implementation details I would revisit

A review of the public source revision used for this write-up surfaced a few gaps worth recording. Because code can change, the implementation-specific observations below should be checked against the current branch before treating them as a live code audit:

- **Pattern coverage is limited.** Regex and heuristics cannot reliably identify every sensitive value, and false positives are possible. The project has no published benchmark measuring detection accuracy.
- **URL checking needs validation.** In the source revision I reviewed, the URL-check method appeared to reference a variable named `content` that was not defined within that method. This path should be retested before the integration is described as working reliably.
- **Some optional controls were not verified.** The monitoring loop checked for clipboard-intrusion and cloud-sync-prevention helper methods, but their definitions were not present in the reviewed public file. I would not describe those settings as verified protection without confirming the implementation.
- **Raw clipboard content may reach a log.** The reviewed risky-command path appeared to log the full matched content. If that behavior remains in the current branch, it should be changed to log the detection type and timestamp rather than the copied text.
- **Cloud clipboard prevention is not a guarantee.** Operating-system synchronization behavior can vary. A small user-space tool cannot promise to stop every form of clipboard access or synchronization.
- **Windows only.** The project uses Windows clipboard APIs, registry settings, Windows notifications, and Windows startup integration. Linux, macOS, and mobile support were not implemented.

The most important follow-up would be to verify and address any raw-content logging, then test the URL-check path and optional controls. Those details matter because a tool intended to protect sensitive information should not create unnecessary exposure of that same information.

## What I learned

Working on ClipGuardian made me think beyond the detection logic. Recognising a password-like string is only one part of the job; I also had to consider what happens after an alert, how long text stays in memory, what might be written to logs, and whether an external API receives related data.

The privacy question also turned out to be less simple than I first expected. Keeping monitoring local sounds straightforward until reputation checks depend on external services. Even clipboard history is a trade-off: it helps users review what happened, but it also means the application is temporarily holding the data it is trying to protect.

The main lesson for me is that a security tool needs to follow the same principles it is trying to promote. If it logs sensitive copied content or presents a best-effort setting as complete prevention, it can create a new problem while trying to solve another. ClipGuardian remains a learning project focused on making clipboard activity more visible and making it easier for a user to clear copied content.
